# AI超级导演能力库体检、去重与维护协议

## 1. 定位

这份协议让 AI超级导演不只会新增能力，也会维护能力库本身。能力库越来越厚以后，最大的风险不是“不够多”，而是入口重复、规则打架、触发词泛滥、README 越来越难读，最后输出反而变慢、变散、变模板。

一句话原则：

```text
真正的进化不是一直加能力，而是让下一次判断更快、更准、更少错。
```

默认目标：

1. 新能力进入前先查重。
2. 能补现有文档时，不急着新增文档。
3. 能写成入口、禁用项、第一刀或回归题时，不写成空泛长文。
4. 重复能力要合并或降级。
5. README 只保留能改变行为的核心入口。

## 2. 什么时候必须启用

遇到以下信号，默认调用本协议：

1. 用户说“继续完善、继续进化、整理一下、别越来越乱、能力太多、查漏补缺、维护能力库、去重”。
2. 连续新增多张能力卡后，需要检查是否重复、冲突或入口过多。
3. 一个新想法可能只是现有能力的补丁。
4. README 默认工作流变长，需要判断新条目是否真的值得进入主流程。
5. 两张文档对同一场景给出不同优先级。
6. 验证发现链接、序号、未完成标记或触发规则异常。

不必启用的情况：

1. 用户只要具体创作交付。
2. 新能力明显是未覆盖的大类型或高风险流程。
3. 只是修错字、链接或格式。

## 3. 维护动作优先级

每次进化前，按顺序判断：

| 优先级 | 动作 | 适合情况 |
| --- | --- | --- |
| 1 | 补入口 | 用户说法没有被正确路由 |
| 2 | 补禁用项 | 反复出现同一类错误 |
| 3 | 补第一刀 | 已有病灶，但缺具体改法 |
| 4 | 补模板 | 已有规则，但输出不好执行 |
| 5 | 补回归题 | 容易退化或重复犯错 |
| 6 | 合并重复 | 两张卡职责高度重叠 |
| 7 | 降级非核心 | 某能力只适合少数场景 |
| 8 | 新增文档 | 现有体系没有入口或跨多能力需要总控 |

判断句：

```text
这次改动能不能只补现有资产？如果可以，不新增文档。
```

## 4. 新能力准入门槛

新增文档必须同时满足至少 3 条：

1. 现有能力没有清晰入口。
2. 问题跨多个能力，需要总控或仲裁。
3. 这个问题会导致生成失败、客户交付失败或重复返工。
4. 它能写出可检查的通过标准。
5. 它能改变下一次输出顺序。
6. 它能减少而不是增加用户追问。
7. 它能给 Seedance 或后期执行明确字段。

不准新增：

1. 只是换一个好听名字。
2. 只是收集漂亮形容词。
3. 已有文档能承载，只是没有补进去。
4. 不能写出触发词、第一刀和通过标准。
5. 只会让 README 更长，但不会让输出更准。

## 5. 重复与冲突检查

### 5.1 重复检查

每次新增前搜索：

```text
触发词：
核心概念：
第一刀：
输出模板：
禁止项：
```

如果两张卡回答同一个问题：

1. 一张做总控。
2. 一张做专项执行。
3. README 只放总控或最常用入口。
4. 专项卡在总控的“与其他能力衔接”里出现。

### 5.2 冲突检查

常见冲突：

| 冲突 | 拍板 |
| --- | --- |
| 合规 vs 创意 | 合规优先 |
| 生成稳定 vs 炫技 | 生成稳定优先 |
| 客户交付 vs 发布传播 | 先分版本 |
| 角色连续性 vs 风格变化 | 角色连续性优先 |
| 产品证明 vs 漂亮空镜 | 产品证明优先 |
| 第一帧抓人 vs 背景解释 | 第一帧抓人优先 |
| 情绪余味 vs 品牌硬露出 | 按客户版/发布版分流 |

如果冲突无法在一条规则里解决，调用能力调用仲裁器。

## 6. README 维护规则

README 不是所有文档的全文目录，而是实战入口。

新增 README 条目必须满足：

1. 用户会用自然语言触发它。
2. 它能改变默认工作流。
3. 它是高频、高风险或高价值入口。
4. 链接必须存在。
5. 不能与相邻条目表达同一件事。

默认工作流条目过长时：

1. 合并同类项。
2. 把低频能力移到核心资产或专项文档，不进入主流程。
3. 保留高风险门禁：口型、文字、角色、动作、交付、合规。
4. 每次改编号后必须重新检查连续性。

## 7. 维护输出卡

默认输出格式：

```text
我先做能力库体检：

这次想补的能力：
【一句话】

已有相近资产：
1. 【文档A】负责：
2. 【文档B】负责：

判断：
新增文档 / 补现有文档 / 补 README 入口 / 加回归题 / 合并重复 / 暂不加入

理由：
【为什么这样处理】

本次动作：
【具体改哪些文件】

验证：
链接：
序号：
未完成标记：
规格数量：
```

## 8. 合并与降级规则

当发现重复能力时，不急着删文件，先降级：

1. README 只留一个主入口。
2. 重复文档在相关文档中改成“专项补充”。
3. 新触发词统一归到主入口。
4. 输出模板只保留最可执行的一版。
5. 回归题只检查主入口是否调用正确。

只有在明确确认某文档无独立价值时，才考虑删除或归档。

## 9. 验证清单

每次维护后，必须检查：

1. 新文件是否存在。
2. README 是否有入口。
3. README 本地链接是否都存在。
4. 默认工作流编号是否连续。
5. 新文档是否无未完成标记。
6. 新能力是否有触发词、第一刀、输出模板或最小合格线。
7. specs 数量是否符合预期。

## 10. 与其他能力衔接

默认顺序：

```text
能力查漏补缺与真人导演成长路线
-> 能力库体检、去重与维护协议
-> 经验回写与版本进化协议
-> 能力调用仲裁器
-> 自我校准与回归测试套件
```

分工：

1. 查漏补缺决定缺什么。
2. 本协议决定怎么补、是否新增、是否合并。
3. 经验回写决定经验写回哪里。
4. 仲裁器处理能力调用冲突。
5. 回归测试检查升级后是否退化。

## 11. 最小合格线

一次能力库维护至少要输出：

1. 这次想补什么。
2. 已有相近资产。
3. 新增、补丁、合并或降级判断。
4. 本次具体动作。
5. README 接入策略。
6. 验证结果。

少一项，就不是维护，只是继续堆文档。
